# Activity 1 – Step 1: A vague prompt

**Chatbot / model:** GitHub Copilot (model name not exposed in this session)

## Prompt

```text
Create tests for a file upload feature
```

## Response

Because the requirements are not specified, these are general test ideas. Confirm the supported file types, size limits, access rules, and failure behavior with the product owner before turning them into definitive pass/fail tests.

| # | Test idea | Expected result |
|---|---|---|
| 1 | Upload a valid file using the file picker. | The file is accepted and appears in the upload result or file list. |
| 2 | Upload a valid file using drag and drop, if supported. | The file is accepted and the same result is shown as with the file picker. |
| 3 | Upload each supported file type. | Supported types are accepted and can be opened or downloaded correctly. |
| 4 | Try an unsupported file type. | The upload is rejected with a clear explanation; no unusable file is stored. |
| 5 | Upload a zero-byte file and a file with ordinary content. | The system follows its documented empty-file policy and handles ordinary files successfully. |
| 6 | Upload files at, just below, and just above the maximum size. | Files within the limit are accepted; files over the limit are rejected with a clear message. |
| 7 | Attempt to upload without selecting a file. | No upload is started, and the user is prompted to select a file. |
| 8 | Upload a file whose name contains spaces, Unicode characters, or punctuation. | The name is displayed and handled correctly without being truncated or interpreted as a path. |
| 9 | Upload a file with a very long name or duplicate an existing file name. | The system applies its documented naming behavior and does not silently overwrite an existing file. |
| 10 | Observe the interface during a slow upload. | Progress is visible and updates; the interface remains responsive. |
| 11 | Cancel an upload partway through, if cancellation is supported. | The upload stops, the user is informed, and no incomplete file is presented as successfully uploaded. |
| 12 | Interrupt the network during upload, then restore it. | The system reports the failure and follows its documented retry/resume behavior without creating a misleading success result or duplicate. |
| 13 | Cause a server-side error during upload. | The user receives a useful failure message, and the file is not shown as successfully saved. |
| 14 | Double-click the upload action or submit the same file repeatedly. | The system prevents unintended duplicate submissions or handles duplicates according to its documented policy. |
| 15 | Upload a file containing potentially unsafe content or a misleading extension. | The system applies its security checks and does not trust the filename or extension alone. |
| 16 | Try a filename containing path traversal characters or script-like text. | The input is handled safely; it cannot escape the intended storage location or execute as code. |
| 17 | Attempt to upload without signing in or without the required permission. | The request is denied and no file is stored. |
| 18 | After upload, try accessing the file through its URL as another user. | Access follows the product's authorization rules; unauthorized users cannot retrieve the file. |
| 19 | Download or open an uploaded file and compare it with the original. | The file contents are intact and have not been corrupted or changed. |
| 20 | Refresh or revisit the file list after a successful upload. | The uploaded file remains available according to the product's persistence rules. |
| 21 | Check the upload result after a failed attempt. | The UI clearly distinguishes failure from success and does not show a failed file as available. |
| 22 | Upload several files in sequence or concurrently, if supported. | Each file has an accurate result; one file's failure does not incorrectly change another's status. |
