# Activity 1 – Step 2: A specific prompt with context

**Chatbot / model:** GitHub Copilot (model name not exposed in this session)

## Prompt

```text
Act as a professional software tester and suggest test ideas for the feature delimited by three hashes. All test ideas should be focused on discovering risks that impact the quality characteristics: Functionality, Data Integrity and Security
###
* As a paralegal, in order to store and share legal documents, I want to be able to securely upload documents.
* Acceptance criteria:
  - Upload should support the following common file formats: PDF, DOCX, TXT
  - The maximum file size should be 20MB
  - When a document is uploaded it should give a progress update to the user
  - Once uploaded, the document must initially be only accessible to the person who has uploaded it
  - A report of the upload and whether it was successful or not will be stored in the auditing feature
###
```

## Response

The following test ideas focus on risks to Functionality, Data Integrity, and Security. Confirm how “20MB” is defined (decimal MB or binary MiB) so the size-boundary tests use the agreed limit.

| # | Quality characteristic | Test idea | Expected result / risk checked |
|---|---|---|---|
| 1 | Functionality | Upload a valid PDF, DOCX, and TXT file separately. | Each supported format is accepted and reported as successfully uploaded. |
| 2 | Functionality, Security | Try an unsupported format, and try a file with a supported extension but content that does not match that format. | Unsupported or mismatched content is rejected safely; it is not stored as a successful upload. The server does not rely only on the filename extension. |
| 3 | Functionality, Data Integrity | Upload files just below, exactly at, and just above the 20MB limit. | Files at or below the agreed limit are accepted; a file above it is rejected with a clear result and is not stored as complete. |
| 4 | Functionality | Upload a file while observing progress from start to completion. | Progress is visible, advances consistently with the upload, and reaches a clear completed state only after the server confirms success. |
| 5 | Functionality, Data Integrity | Upload over a slow or interrupted connection. | The user receives accurate progress and a clear failure or completion result; an interrupted or partial transfer is not presented as a complete document. |
| 6 | Functionality, Data Integrity | Cause an upload to fail (for example, by making the service unavailable) and inspect the user-facing result and audit record. | The failure is reported to the user and recorded as unsuccessful; no success state or complete document is created incorrectly. |
| 7 | Functionality, Data Integrity | Complete a successful upload and inspect its audit record. | The audit feature records the outcome as successful and associates it with the correct uploader and document/upload event. |
| 8 | Data Integrity | Compare the uploaded document with the original by opening or downloading it after upload. | The document contents remain intact; no truncation, corruption, or unintended modification occurs. |
| 9 | Data Integrity | Submit the same upload more than once, including a repeated submission after a slow response. | Each attempt has an accurate outcome in the UI and audit record; retries do not silently overwrite or create misleading duplicate records. |
| 10 | Security | Sign in as a second user and try to find or open the newly uploaded document through the normal interface and document URL/API. | Only the uploader can access the document initially; another user is denied, including when they know or guess its identifier or URL. |
| 11 | Security | Try accessing the document while signed out, then as the uploader and as another signed-in user. | Anonymous access is denied, the uploader can access their document, and another user cannot bypass the ownership check. |
| 12 | Security | Attempt to change the document or uploader identifier in a request when viewing or downloading a document. | Authorization is enforced on the server for each request; changing identifiers does not expose another user's document. |
| 13 | Security, Data Integrity | Upload filenames containing path separators, traversal-like sequences, HTML/script markup, or unusual Unicode characters. | Names are handled as data, safely displayed and stored; they cannot escape the intended storage area or execute in the interface. |
| 14 | Security | Upload a file containing content that could be interpreted as active content, then preview or download it if those actions are available. | The content is not executed in the application context, and access remains restricted to the uploader. |
| 15 | Security, Data Integrity | Inspect audit records using a user who is not authorized to view them; check that records are not editable by ordinary users. | Audit information is protected from unauthorized viewing or tampering, and upload outcomes remain trustworthy. |
| 16 | Data Integrity, Security | Check audit records for both successful and failed attempts, including retries. | Each attempt has the correct outcome and is associated with the right user and upload; records do not falsely indicate success or disclose document contents unnecessarily. |
